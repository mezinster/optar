# Що показано, а що ні { #what-has-and-has-not-been-shown }

У цьому розділі сказано, на чому ґрунтуються твердження проєкту. Здебільшого
вони спираються на змодельовані скани, а не на папір.

## Змодельовані скани { #simulated-scans }

Автоматичні тести зчитують згенеровані зображення з розмиттям, шумом і
поворотом. Змодельоване розмиття підібрано за трьома справжніми сканами
однієї надрукованої сторінки з роздільною здатністю 300 dpi, зробленими на
одному принтері й одному протяжному сканері.

- За такого розмиття стандартні точки з 300 dpi звичайним методом зчитування
  не декодувалися.
- Середні точки зі стандартним захистом пройшли перевірку з 300 dpi і з
  200 dpi.
- Великі, крупні й дуже крупні точки пройшли перевірку з 200 dpi без помилок.
- Документ із 12 сторінок пройшов перевірку з однією вилученою сторінкою.

## Повільний метод { #the-slower-reader }

[Повільний метод](slower-reader.md) показано на одному справжньому документі
й одному змодельованому.

**Справжній.** Документ власника з шести сторінок A4, стандартні точки,
високий захист, відсканований приблизно з 290 dpi, хоча рекомендовано
600 dpi. Звичайний метод не розпізнав жодної сторінки. З повільним методом
файл було відновлено й перевірено за його відбитком: 759 879 байтів, з яких
41 495 байтів виправив захист документа, а найгірший блок використав 40 із
64 одиниць свого ресурсу. Це один документ, один принтер, один сканер і одна
роздільна здатність. Скани не входять до репозиторію.

**Змодельований** (`tests/unit/test_coarse_claim.py`). Документ із двох
сторінок того самого типу, відсканований з 290 і з 300 dpi з розмиттям
1,8 точки принтера. З 290 dpi звичайний метод не розпізнає жодної сторінки; з
300 dpi він зчитує напис кожної сторінки, але не заголовок. В обох випадках
файл проходить перевірку з повільним методом. За типового розмиття симулятора
(1,0) звичайний метод сам зчитує таку сторінку з 300 dpi.

Симулятор м’якший за сканер власника: з 290 dpi у моделюванні повільний метод
нічого не виправив, тоді як у справжньому документі довелося виправити
41 495 байтів.

Стандартний захист має ресурс 32, менше за 40, яких потребував найгірший блок
справжнього документа. Тож очікується, що документ зі стандартним захистом,
відсканований так само, відновити не вдасться. Старі сторінки у стилі
версії 0.2 повільний метод не охоплює.

## Що не показано { #what-is-not-shown }

- Жодного справжнього скану сторінки з більшими точками ще не зчитано.
- Зчитування написів і декодування мають автоматичні тести лише на
  синтетичних сканах, а не на справжніх надрукованих і відсканованих
  сторінках. Це стосується й кожної роздруківки з більшими точками або із
  захистом.
- Протяжні сканери не випробувано, крім того, що програма знайшла сітку точок
  на трьох справжніх сканах.
- Три справжні скани однієї роздруківки, зроблені з 300 dpi, за вимірюванням
  відповідали приблизно 286 dpi, тобто ця роздруківка вийшла приблизно у 95% фактичного
  розміру. Менші точки зчитати важче, тому друкуйте у фактичному розмірі
  (100%).
- Струменеві принтери не випробувано.

## Ті самі сторінки, що й у програми на C { #the-same-pages-as-the-c-program }

Сторінки кодувальника на Python побайтово збігаються з результатом
оригінальної програми `optar` на C для A4, Letter і всіх п’яти режимів
корекції помилок. Позиції хрестів і зчитані біти декодера на Python побітово
збігаються з результатами `unoptar` на C на синтетичних тестових зображеннях.
Обидва результати порівнюють із результатами програм на C, які записали один раз
і зберігають у `tests/vectors`.

Кожна сторінка роздруківки із самоідентифікацією залишається звичайною
сторінкою optar: `unoptar` на C, зібраний із тим самим розміром сітки, точно
зчитує її точки (записано для крупних точок на A4 і середніх точок на
Letter). Повертає він дані, у які разом із файлом загорнуто додаткові
відомості й захист, а не сам файл.
