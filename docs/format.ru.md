# Формат optar { #the-optar-format }

Нормативным является английский текст этой спецификации, [The optar format](https://mezinster.github.io/optar/format/): формат определяют он и тестовые векторы в `tests/vectors`. Этот перевод справочный; если он расходится с английским текстом, действует английский текст.

optar хранит файл на бумаге в виде страниц из чёрных и белых точек.
Спецификация определяет, что такое страница и что такое документ (набор страниц,
несущий один файл), чтобы можно было написать кодировщик, страницы которого
читает этот проект, и декодер, читающий страницы этого проекта.

Документ состоит из восьми частей:

1. Термины и соглашения
2. Страница (версия 0)
3. Метка документа (распечатки 0.2.0)
4. Самоопознающиеся документы (версия 1)
5. Печать
6. Что должна делать программа чтения
7. Эталонный декодер (справочно)
8. История

Части с 1 по 6 нормативные. Слово «должен» (must) употребляется только в
требованиях к тому, чем является страница или документ, а в части 6 — к тому,
что программа чтения делает с прочитанным. Как программа чтения находит
страницу на скане и снимает с неё отсчёты, к формату не относится; часть 7
описывает, как это делает этот проект.

Формат закреплён тестовыми векторами в `tests/vectors`. Каждый нормативный
раздел заканчивается строкой «Векторы:» с именами файлов, которые его
закрепляют; как читается каждый файл, сказано в `tests/vectors/README.md`.
Таблицы, перед которыми стоит комментарий `spec-table`, и блоки с пометкой
`example` сравниваются с кодом в `tests/unit/test_spec.py`.

## 1. Термины и соглашения { #1-terms-and-conventions }

### 1.1 Числа, биты и байты { #11-numbers-bits-and-bytes }

- Все целые числа записаны в десятичной системе, если у них нет префикса `0x`.
- `a // b` — деление с округлением вниз, `a mod b` — его остаток, `ceil(a / b)` —
  деление с округлением вверх. Все три применяются только к неотрицательным
  целым числам.
- Счёт и индексы начинаются с 0, кроме номеров страниц и граней
  додекаэдра в разделе 2.5, которые начинаются с 1.
- **Битовая строка** читается начиная со старшего бита: бит `n` байтовой
  строки — это бит `7 - (n mod 8)` байта `n // 8`, где бит 7 байта — его
  старший бит. У слова из `w` битов, взятого из битовой строки, старшим битом
  является первый бит строки.
- Многобайтовые целые числа в заголовке (раздел 4.2) записаны старшим байтом
  вперёд (big-endian).
- SHA-256 и CRC-32 — обычные функции. CRC-32 — та, что в zlib, PNG
  и Ethernet: отражённый многочлен `0xEDB88320`, начальное значение и итоговый
  XOR `0xFFFFFFFF`.

### 1.2 Пиксели и цвета { #12-pixels-and-colours }

- **Страница** — прямоугольное изображение из **пикселей страницы**. Каждый
  пиксель страницы либо чёрный, либо белый.
- Чёрный пиксель данных — это бит 1; белый пиксель данных — бит 0.
- В 8-битных файлах изображений в оттенках серого чёрный пиксель имеет
  значение 0, а белый — значение 255. Других кодировок изображения эта
  спецификация не использует.
- Координаты страницы — `(x, y)`: `x` считает столбцы от левого края, `y`
  считает строки от верхнего края, оба от 0. Страница печатается и читается
  в прямом положении, с полосой надписи (раздел 2.8) внизу.
- **Координаты области данных** `(u, v)` не учитывают рамку (раздел 2.2):
  `u = x - border`, `v = y - border`.

### 1.3 Единицы { #13-units }

- **Пункт** (pt) равен 1/72 дюйма.
- **Точка принтера** равна 1/600 дюйма: одна точка устройства принтера с
  разрешением 600 dpi, для которого сделаны макеты.
- **Точка данных** — один пиксель страницы в напечатанном виде. Это квадрат
  из целого числа точек принтера (раздел 5.1). **Стандартная** точка данных
  имеет ширину 3 точки принтера, то есть 1/200 дюйма.

### 1.4 Виды документов { #14-kinds-of-document }

**Поток** — байтовая строка, которую страницы документа несут в своих
пикселях данных. Существуют три вида документов; все три состоят из одинаковых
страниц версии 0 (часть 2).

| Вид | Кто записывает | Поток — это | Надпись несёт |
|---|---|---|---|
| простой | первоначальная программа на C, optar 0.1.0, `--no-tag` | файл | только произвольный текст |
| с меткой | optar 0.2.0 и более поздние («совместимая») | файл | метку (часть 3) |
| самоопознающийся | optar 0.3.0 и более поздние | контейнер (часть 4) | только произвольный текст |

## 2. Страница (версия 0) { #2-the-page-version-0 }

### 2.1 Формат страницы и строка формата { #21-the-page-format-and-the-format-string }

**Формат страницы** — это восемь неотрицательных целых чисел:

| Поле | Имя | Смысл | Должно быть |
|---|---|---|---|
| 1 | `version` | версия формата страницы | 0 |
| 2 | `xcrosses` | крестов в строке | не менее 2 |
| 3 | `ycrosses` | крестов в столбце | не менее 2 |
| 4 | `cpitch` | расстояние между началами крестов | больше `2 * chalf` |
| 5 | `chalf` | половина стороны креста | не менее 1 |
| 6 | `fec_order` | код страницы | от 1 до 5 |
| 7 | `border` | толщина рамки | не менее 1 |
| 8 | `text_height` | строк в полосе надписи | `LABEL_HEIGHT` |

**Строка формата** — это восемь полей в указанном порядке, в десятичной записи
без ведущих нулей, соединённые знаком `-`. Каждая страница печатает свою строку
формата в надписи (раздел 2.8). Страницы, которые печатает этот проект,
различаются только полями `xcrosses` и `ycrosses`; остальные поля имеют
значения из раздела 1.5. Десять форматов страниц, которые он печатает,
перечислены в разделе 5.2. Страницы с другими значениями тоже являются
действительными страницами и читаются, если программе чтения дана строка формата.

Все размеры ниже указаны в пикселях страницы.

    data_width  = cpitch * (xcrosses - 1) + 2 * chalf
    data_height = cpitch * (ycrosses - 1) + 2 * chalf
    width       = 2 * border + data_width
    height      = 2 * border + data_height + text_height

```example
a4_data_width = 1542
a4_data_height = 2214
a4_width = 1546
a4_height = 2242
```

Имена с префиксом `a4_` относятся к формату `0-65-93-24-3-1-2-24`,
стандартной странице A4.

Векторы: `tests/vectors/c/encoder_pages.json`.

### 2.2 Части страницы { #22-the-parts-of-a-page }

Страница имеет `width` столбцов и `height` строк. Сверху вниз:

| Строки `y` | Содержимое |
|---|---|
| от `0` до `border - 1` | рамка: чёрные |
| от `border` до `border + data_height - 1` | столбцы от `0` до `border - 1` и последние `border` столбцов: чёрные. Между ними — **область данных**, `data_width` столбцов |
| от `border + data_height` до `border + data_height + text_height - 1` | **полоса надписи**: чёрная по всей ширине, с надписью, нарисованной белым в столбцах от `border` до `border + data_width - 1` (раздел 2.8) |
| последние `border` строк | рамка: чёрные |

```example
a4_label_top_row = 2216
```

Каждый пиксель области данных либо входит в крест (раздел 2.3), либо является
пикселем данных (раздел 2.4).

Векторы: `tests/vectors/c/encoder_pages.json`.

### 2.3 Кресты { #23-crosses }

Область данных содержит `xcrosses * ycrosses` **крестов**, по которым
программа чтения находит пиксели данных. Крест `(i, j)`, `0 <= i < xcrosses`,
`0 <= j < ycrosses`, — это квадрат `2 * chalf` на `2 * chalf` пикселей, верхний
левый пиксель которого, его **начало**, находится в координатах области данных
`(i * cpitch, j * cpitch)`. Четыре его четверти размером `chalf` на `chalf`
пикселей:

| Четверть | Цвет |
|---|---|
| верхняя левая | чёрная |
| верхняя правая | белая |
| нижняя левая | белая |
| нижняя правая | чёрная |

Первый крест касается верхнего левого угла области данных, а последний — её
нижнего правого угла. Пиксель `(u, v)` области данных входит в крест тогда
и только тогда, когда `u mod cpitch < 2 * chalf` и `v mod cpitch < 2 * chalf`.

```example
a4_last_cross_x = 1538
a4_last_cross_y = 2210
```

Это координаты страницы `(x, y)` начала последнего креста.

Векторы: `tests/vectors/c/encoder_pages.json`.

### 2.4 Пиксели данных и их порядок { #24-data-pixels-and-their-order }

**Пиксели данных** — это пиксели области данных, не входящие в кресты. Они
нумеруются от 0 в порядке чтения: по строкам сверху вниз, а внутри строки
слева направо. Номер пикселя данных — его **позиция в канале**; `total_bits` —
число пикселей данных.

Строки области данных повторяются с периодом `cpitch`:

- **узкая полоса** из `2 * chalf` строк, проходящих через кресты. Каждая строка
  содержит `narrow_width` пикселей данных в `xcrosses - 1` промежутках по
  `gap_width` пикселей между крестами;
- **широкая полоса** из `gap_width` строк без крестов. Каждая строка содержит
  `data_width` пикселей данных.

Последний период состоит только из узкой полосы.

    gap_width     = cpitch - 2 * chalf
    narrow_width  = gap_width * (xcrosses - 1)
    narrow_pixels = 2 * chalf * narrow_width
    wide_pixels   = gap_width * data_width
    rep_pixels    = narrow_pixels + wide_pixels
    total_bits    = rep_pixels * (ycrosses - 1) + narrow_pixels

Координаты области данных `(u, v)` позиции в канале `n` (narrow strip — узкая
полоса, wide strip — широкая):

    rep = n // rep_pixels
    s   = n mod rep_pixels
    if s < narrow_pixels:                      (narrow strip)
        row = s // narrow_width
        r   = s mod narrow_width
        u   = 2 * chalf + (r // gap_width) * cpitch + r mod gap_width
        v   = rep * cpitch + row
    else:                                      (wide strip)
        s   = s - narrow_pixels
        u   = s mod data_width
        v   = rep * cpitch + 2 * chalf + s // data_width

Координаты страницы — `(u + border, v + border)`.

```example
a4_narrow_width = 1152
a4_narrow_pixels = 6912
a4_wide_pixels = 27756
a4_rep_pixels = 34668
a4_total_bits = 3196368
a4_xy_of_0 = 6, 0
a4_xy_of_17 = 23, 0
a4_xy_of_18 = 30, 0
a4_xy_of_1152 = 6, 1
a4_xy_of_6912 = 0, 6
a4_xy_of_8454 = 0, 7
a4_xy_of_34668 = 6, 24
a4_xy_of_3196367 = 1535, 2213
```

`a4_xy_of_N` — это `u, v` позиции в канале `N`.

Векторы: `tests/vectors/c/bit_placement.json`.

### 2.5 Код страницы { #25-the-page-code }

Данные страницы разрезаются на **слова** по `small` битов. Каждое слово
кодируется в **символ** из `large` битов, который можно скорректировать, если
несколько его битов прочитаны неверно. Код выбирается полем `fec_order`:

| `fec_order` | Код | `large` | `small` |
|---|---|---|---|
| 1 | Голея (24, 12) | 24 | 12 |
| от 2 до 5 | расширенный код Хэмминга | `2 ^ fec_order` | `large - 1 - fec_order` |

```example
code_bits_of_order_1 = 24, 12
code_bits_of_order_2 = 4, 1
code_bits_of_order_3 = 8, 4
code_bits_of_order_4 = 16, 11
code_bits_of_order_5 = 32, 26
```

Символ записывается здесь как целое число из `large` битов; его **бит `b`**
в том порядке, в каком биты размещаются на странице, отсчитывается от старшего
бита: бит 0 — это бит со значением `2 ^ (large - 1)`.

#### Код Голея (24, 12) { #golay-24-12 }

Символ 12-битного слова `d` равен `d * 4096 + p(d)`: слово в старших
12 битах, под ним 12 битов чётности. Биты чётности получаются из додекаэдра,
грани которого пронумерованы от 1 до 12. Грань `f` соответствует биту слова `d`
со значением `2 ^ (f - 1)`. У каждой грани пять соседних:

<!-- spec-table: golay -->
| Грань | Соседние грани | Маска |
|---|---|---|
| 1 | 2, 3, 4, 5, 6 | `0xfc1` |
| 2 | 1, 3, 6, 7, 8 | `0xf1a` |
| 3 | 1, 2, 4, 8, 9 | `0xe74` |
| 4 | 1, 3, 5, 9, 10 | `0xcea` |
| 5 | 1, 4, 6, 10, 11 | `0x9d6` |
| 6 | 1, 2, 5, 7, 11 | `0xbac` |
| 7 | 2, 6, 8, 11, 12 | `0x35d` |
| 8 | 2, 3, 7, 9, 12 | `0x6b9` |
| 9 | 3, 4, 8, 10, 12 | `0x573` |
| 10 | 4, 5, 9, 11, 12 | `0x2e7` |
| 11 | 5, 6, 7, 10, 12 | `0x58f` |
| 12 | 7, 8, 9, 10, 11 | `0x83f` |

В маске грани `r` стоит 1 для каждой грани, не соседней с `r` (включая саму
грань `r`). Бит чётности грани `r` равен 1, если в `d AND mask` нечётное число
единичных битов. Это бит `p(d)` со значением `2 ^ (12 - r)`: грань 1 даёт
старший бит чётности, грань 12 — младший.

```example
golay_0x001 = 0x00183f
golay_0x800 = 0x800fc1
golay_0xabc = 0xabca13
golay_0xfff = 0xffffff
```

Код линейный, слову 0 соответствует символ 0, и любые два символа различаются
не менее чем в 8 битах. Поэтому для символа, прочитанного с 3 или менее
неверными битами, существует ровно один символ, отличающийся от него не более
чем на 3 бита, — тот, что был напечатан. Файл векторов закрепляет все
4096 символов.

#### Расширенный код Хэмминга (`fec_order` от 2 до 5) { #extended-hamming-fec_order-2-to-5 }

Пронумеруем биты символа по их значению: позиция `q` — это бит со значением
`2 ^ q`, `0 <= q < large`.

1. Биты слова, начиная со старшего, помещаются в позиции, которые не равны 0
   и не являются степенью двойки, от позиции `large - 1` вниз.
2. Для `i` от 0 до `fec_order - 1` позиция `2 ^ i` устанавливается так, чтобы
   в позициях, номер которых имеет установленный бит `i`, было чётное число
   единичных битов.
3. Позиция 0 устанавливается так, чтобы во всём символе было чётное число
   единичных битов.

Такой символ можно скорректировать, если неверен один бит, а два неверных бита
обнаруживаются. При `fec_order` 2 символ — это единственный бит слова,
повторённый четыре раза.

```example
hamming_2_of_1 = 1111
hamming_3_of_1011 = 10101010
hamming_4_of_10000000001 = 1000000100011000
hamming_5_of_1 = 00000000000000000000000000001111
```

В каждой строке после `of_` дано слово в двоичной записи, а справа — его
символ в двоичной записи, начиная со старшего бита.

Векторы: `tests/vectors/c/golay.json`, `tests/vectors/c/encoder_pages.json`.

### 2.6 Символы на странице { #26-symbols-on-the-page }

Страница содержит

    symbols   = total_bits // large
    used_bits = symbols * large
    net_bits  = symbols * small

`net_bits` — число битов данных, которые несёт страница. Символы подвергаются
перемежению, так что соседние пиксели принадлежат разным символам:

    bit b of symbol s is at channel position  s + b * symbols

(бит `b` символа `s` находится в позиции в канале `s + b * symbols`)
для `0 <= s < symbols` и `0 <= b < large`. Таким образом, с кодом Голея пиксели
данных образуют 24 идущие подряд группы по `symbols` пикселей, и у каждого
символа в каждой группе по одному пикселю, на одном и том же месте.

Пиксели данных в позициях в канале от `used_bits` и выше не принадлежат
никакому символу и белые.

```example
a4_symbols = 133182
a4_used_bits = 3196368
a4_net_bits = 1598184
a4_position_of_symbol_1000_bit_5 = 666910
a4_xy_of_666910 = 1306, 462
a4_medium_total_bits = 1838484
a4_medium_symbols = 76603
a4_medium_unused_bits = 12
a4_medium_net_bits = 919236
hamming_2_net_bits = 799092
hamming_3_net_bits = 1598184
hamming_4_net_bits = 2197503
hamming_5_net_bits = 2597036
```

Имена с `a4_medium_` относятся к формату `0-50-70-24-3-1-2-24`;
`hamming_N_net_bits` — к сетке A4 с `fec_order` N.

Векторы: `tests/vectors/c/bit_placement.json`, `tests/vectors/c/encoder_pages.json`.

### 2.7 От потока к страницам { #27-from-a-stream-to-pages }

Пусть поток имеет длину `nbytes` байт и читается как битовая строка (раздел 1.1).

    pages = ceil(8 * nbytes / net_bits)

Страница `p` (считая от 1) несёт биты потока с `(p - 1) * net_bits` по
`p * net_bits - 1`. Слово `s` страницы — это `small` битов, начинающихся
с бита `s * small` битов страницы, а символ `s` — его код (раздел 2.5).

- Биты за концом потока равны 0. Поэтому последнее слово, содержащее биты
  потока, дополняется нулевыми битами в младших разрядах, а все следующие
  слова последней страницы равны 0. Символ слова 0 равен 0, поэтому такие
  слова печатаются белыми пикселями.
- Документ имеет не более `MAX_PAGES` страниц; более длинный поток закодировать
  нельзя.
- Пустой поток (`nbytes = 0`) даёт `pages = 0`. Он печатается как одна
  страница, все пиксели данных которой белые, а надпись даёт номер страницы 1
  и число страниц 0 (`1/0`).

Если прочитать страницы по порядку и соединить их `net_bits` битов, получится
поток, за которым идут нулевые биты. Страница не записывает, где кончается
поток: простой документ возвращает свой файл, дополненный нулевыми байтами до
конца последней страницы (без битов, не составляющих целого байта, если
`net_bits` не кратно 8). И метка (часть 3), и контейнер (часть 4) записывают
размер файла.

```example
a4_pages_for_0_bytes = 0
a4_pages_for_1_byte = 1
a4_pages_for_199773_bytes = 1
a4_pages_for_199774_bytes = 2
a4_words_for_1000_bytes = 667
```

Поток из 1000 байт заполняет 667 слов первой страницы; последнее из них
содержит 8 битов потока и четыре нулевых бита.

Векторы: `tests/vectors/c/encoder_pages.json`.

### 2.8 Надпись { #28-the-label }

Полоса надписи содержит одну строку текста — для людей, а в документе с меткой
и для программы чтения. Она рисуется фиксированным шрифтом.

**Лента шрифта** — изображение из `LABEL_HEIGHT` строк и 1500 столбцов, каждый
пиксель которого чёрный или белый. Столбцы от `0` до
`TEXT_WIDTH * GLYPH_CELLS - 1` содержат `GLYPH_CELLS` ячеек знаков по
`TEXT_WIDTH` столбцов: ячейка знака с кодом `c`, `32 <= c <= 126`, начинается
со столбца `TEXT_WIDTH * (c - FIRST_CHAR)`. Остальные столбцы содержат логотип.
Глифы и логотип белые на чёрном. Лента — это файл `src/optar/data/font.png`
этого проекта (его пиксель белый, если значение серого 128 или больше);
приведённый ниже дайджест — это SHA-256 его пикселей в виде байтов 0 (чёрный)
и 255 (белый), по строкам.

```example
strip_width = 1500
logo_width = 265
glyph_column_of_capital_a = 429
font_strip_sha256 = 481c0abd7884afb5ab6d958fbb95c0d6be97b0e2a7124f57e1abcd118d7d4bc4
```

**Строка надписи** страницы `page` из `total` с произвольным текстом `text`
такова (два пробела, строка формата, пробел, `page`, «/», `total`, пробел, `text`):

    two spaces, the format string, a space, page, "/", total, a space, text

`page` и `total` записываются в десятичной системе без ведущих нулей. Пробел
после `total` ставится и тогда, когда `text` пуст. Затем строка обрезается до
первых `data_width // TEXT_WIDTH - 1` знаков (кодовых точек Unicode).

**Рисование.** Полоса имеет ширину `data_width` столбцов, нумеруемых от 0 со
столбца страницы `border`; всё, что в ней не нарисовано, чёрное.

1. Если `logo_width <= data_width`, логотип копируется в столбцы полосы от `0`
   до `logo_width - 1`.
2. Курсор начинается в столбце полосы `logo_width` независимо от того, был ли
   нарисован логотип.
3. Для каждого знака обрезанной строки по порядку: знак с кодом меньше 32 или
   больше 127 пропускается. Иначе, если курсор плюс `TEXT_WIDTH` не больше
   `data_width`, `TEXT_WIDTH` столбцов ленты, начиная с
   `TEXT_WIDTH * (code - FIRST_CHAR)`, копируются в полосу в позицию курсора;
   в обоих случаях курсор сдвигается на `TEXT_WIDTH`.

Три следствия, которые кодировщик должен воспроизвести, чтобы печатать такие
же страницы:

- Страница показывает не более `(data_width - logo_width) // TEXT_WIDTH`
  знаков, а это меньше длины, до которой обрезается строка; остальное не
  рисуется.
- Знаки с кодами вне диапазона от 32 до 127 не занимают ячейки, но учитываются
  в длине, до которой обрезается строка.
- Код 127 занимает ячейку и рисует первые `TEXT_WIDTH` столбцов логотипа.
  Такую надпись прочитать обратно нельзя.

```example
a4_label_line = "  0-65-93-24-3-1-2-24 3/7 backup.tar"
a4_label_characters = 117
a4_label_cells = 98
a4_xlarge_label_cells = 18
```

`a4_label_characters` — длина, до которой обрезается строка, а
`a4_label_cells` — число знаков, которые показывает страница. Страница формата
`0-22-31-24-3-1-2-24` показывает 18 знаков — меньше, чем в её строке формата;
как такие страницы подписываются при печати, сказано в разделе 5.4.

Векторы: `tests/vectors/c/label.json`, `tests/vectors/c/encoder_pages.json`.

## 3. Метка документа (распечатки 0.2.0) { #3-the-document-tag-020-printouts }

Простой документ не сообщает, какой длины его файл, какие страницы относятся
друг к другу и правильно ли прочитан файл. **Документ с меткой** сообщает это
в произвольном тексте каждой надписи. Его поток — сам файл, поэтому его
страницы читают и программы, ничего не знающие о метке.

### 3.1 Метка { #31-the-tag }

Для файла размером `size` байт:

- `SIZE` — это `size` в десятичной записи без ведущих нулей (`0` для пустого
  файла), не более `MAX_SIZE_DIGITS` цифр;
- `FINGERPRINT` — первые `FINGERPRINT_DIGITS` знаков SHA-256 файла в записи
  строчными шестнадцатеричными цифрами;
- `CHECK` для страницы `page` из `total` — первые `CHECK_DIGITS` знаков
  SHA-256 текста ASCII `SIZE:FINGERPRINT:page/total` в записи строчными
  шестнадцатеричными цифрами, где `page` и `total` записаны так же, как в
  строке надписи.

Метка страницы — текст `[SIZE:FINGERPRINT:CHECK]`. Произвольный текст надписи
страницы — это метка либо метка, один пробел и имя. `SIZE` и `FINGERPRINT`
одинаковы на всех страницах документа; `CHECK` меняется от страницы к странице.

Пустой файл — это одна страница с надписью `1/0` (раздел 2.7); её контрольное
значение вычисляется с `page` 1 и `total` 0.

```example
tag_fingerprint_of_x = 2d711642
tag_check_input = "1:2d711642:1/1"
tag_check_of_x_page_1_of_1 = ca
tag_free_text = "[1:2d711642:ca] name.tar"
tag_of_empty_file = "[0:e3b0c442:e0]"
```

Первые четыре строки относятся к однобайтовому файлу `x`, напечатанному с
именем `name.tar`.

Векторы: `tests/vectors/py/tag.json`.

### 3.2 Когда метка действительна { #32-when-a-tag-is-valid }

Произвольный текст надписи **начинается с метки**, если он начинается с `[`,
размера, как описано выше, `:`, ровно 8 знаков из `0-9a-f`, `:`, ровно 2 знаков
из `0-9a-f` и `]`, а за меткой следует пробел или конец текста.

Метка, прочитанная со страницы `page` из `total` в формате страницы `F`,
**действительна**, если выполнены оба условия:

- её контрольное значение равно контрольному значению, вычисленному по
  прочитанным размеру, отпечатку, `page` и `total`;
- размер соответствует числу страниц: `size = 0` и `total = 0` либо `size > 0`,
  `total > 0` и `(total - 1) * capacity < size <= total * capacity`, где
  `capacity = net_bits // 8` формата `F`.

В двух макетах `standard` (раздел 5.2) `net_bits` кратно 8, поэтому размер
соответствует ровно тому числу страниц, которое даёт ему раздел 2.7. Программа
чтения этого проекта опознаёт страницы по метке только в этих двух макетах.

Векторы: `tests/vectors/py/tag.json`.

## 4. Самоопознающиеся документы (версия 1) { #4-self-identifying-documents-version-1 }

**Самоопознающийся документ** несёт в данных каждой страницы заголовок,
сообщающий, к какому документу относится страница и какая это страница; кроме
того, он может нести чётность, по которой исправляются повреждённые и
восстанавливаются отсутствующие страницы. Файл, его имя и чётность упаковываются в поток —
**контейнер**, и этот поток печатается как обычные страницы версии 0 (часть 2).
Версия 1 — это версия контейнера; формат страницы сохраняет версию 0.

### 4.1 Размеры { #41-sizes }

Для формата страницы `F`, уровня чётности `parity` (раздел 4.4) и числа страниц
`T`:

    page_bytes = net_bits // 8                         payload of one page
    page_body  = page_bytes - HEADER_COPIES * HEADER_SIZE
    k          = CODEWORD - parity                     data bytes of a codeword
    m(T)       = T * page_body // CODEWORD             codewords
    D(T)       = m(T) * k                              bytes of the data region

(`page_bytes` — полезная нагрузка одной страницы, `k` — байты данных кодового
слова, `m(T)` — число кодовых слов, `D(T)` — байты зоны данных.)

**Полезная нагрузка** страницы — её первые `page_bytes * 8` битов данных в виде
байтов. **Тело** страницы — её полезная нагрузка без копий заголовка (раздел
4.3), `page_body` байт. **Тело документа** — соединённые тела страниц с 1 по
`T`, `T * page_body` байт.

Формат страницы может нести контейнер, только если
`page_bytes // HEADER_COPIES >= HEADER_SIZE`.

```example
a4_page_bytes = 199773
a4_page_body = 199583
```

Векторы: `tests/vectors/py/container.json`.

### 4.2 Заголовок { #42-the-header }

Заголовок занимает `HEADER_SIZE` байт:

<!-- spec-table: header-fields -->
| Смещение | Размер | Поле | Тип | Содержимое |
|---|---|---|---|---|
| 0 | 4 | `magic` | байты | `HEADER_MAGIC` |
| 4 | 1 | `version` | целое | `CONTAINER_VERSION` |
| 5 | 1 | `parity` | целое | байтов чётности на кодовое слово: 0, 32 или 64 |
| 6 | 2 | `page` | целое | номер этой страницы, от 1 |
| 8 | 2 | `total` | целое | страниц в документе |
| 10 | 8 | `size` | целое | размер файла в байтах |
| 18 | 16 | `fingerprint` | байты | первые `FINGERPRINT_SIZE` байт SHA-256 файла |
| 34 | 4 | `crc` | целое | CRC-32 байтов с 0 по 33 |

Целые числа записаны старшим байтом вперёд. Все поля, кроме `page` (а вместе с
ним и `crc`), одинаковы на всех страницах документа.

```example
header_bytes = 6f5074310140000300070000000000086e3c000102030405060708090a0b0c0d0e0f1ef0ca9d
header_crc = 0x1ef0ca9d
```

Это заголовок страницы 3 из 7 файла размером 552508 байт с чётностью 64,
отпечаток которого — байты от `00` до `0f`.

Векторы: `tests/vectors/py/container.json`.

### 4.3 Полезная нагрузка страницы { #43-the-payload-of-a-page }

Копия `c` заголовка страницы, `0 <= c < HEADER_COPIES`, занимает байты полезной
нагрузки

    c * (page_bytes // HEADER_COPIES)   to   c * (page_bytes // HEADER_COPIES) + HEADER_SIZE - 1

Остальные байты полезной нагрузки по порядку образуют тело страницы.

```example
a4_header_offsets = 0, 39954, 79908, 119862, 159816
```

Векторы: `tests/vectors/py/container.json`.

### 4.4 Уровни чётности { #44-parity-levels }

<!-- spec-table: parity -->
| Название | Байты чётности | Байты данных |
|---|---|---|
| none | 0 | 255 |
| standard | 32 | 223 |
| high | 64 | 191 |

«Байты чётности» — это поле заголовка `parity`; «Байты данных» — это `k`.
У документа с чётностью 0 есть заголовки и имя, но ничего не исправляется.

Векторы: `tests/vectors/py/container.json`.

### 4.5 Код Рида — Соломона { #45-the-reed-solomon-code }

**Кодовое слово** — это `CODEWORD` байт: `k` байтов данных, за которыми следуют
`parity` байтов чётности.

- Байты — элементы GF(256) с многочленом поля
  `x^8 + x^4 + x^3 + x^2 + 1` (`0x11D`): байт — это многочлен над GF(2),
  коэффициент при `x^7` которого — его старший бит; сложение — это XOR,
  а умножение — умножение многочленов по модулю многочлена поля.
- `alpha` — элемент `0x02`.
- Порождающий многочлен —
  `g(x) = (x - alpha^0)(x - alpha^1) ... (x - alpha^(parity - 1))`.
- Байт `i` кодового слова, `0 <= i <= 254`, — коэффициент при `x^(254 - i)`
  многочлена кодового слова `c(x)`.
- Байты данных — коэффициенты при степенях от `x^254` до `x^parity`. Байты
  чётности выбираются так, чтобы `g(x)` делил `c(x)`: это остаток от деления
  многочлена данных (с нулевыми коэффициентами ниже `x^parity`) на `g(x)`,
  начиная с коэффициента при `x^(parity - 1)`.

Кодовое слово можно исправить, если `2 * e + f <= parity`, где `f` — число его
байтов, о которых известно, что они нечитаемы (стирания), а `e` — число прочих
неверных байтов.

```example
gf_alpha_8 = 0x1d
gf_alpha_254 = 0x8e
rs_32_parity_of_one = 744034ae367e10c2a221219db0c5e10c3b37fde4942fb3b9188afd148e37ac58
rs_32_parity_of_counting = 41841183b11fdb537421939696cda70e1db5c86684af222564b89cc6069f172e
```

`rs_32_parity_of_one` — чётность при parity 32 для 223 байтов данных, которые
все равны нулю, кроме последнего байта, равного 1; это коэффициенты `g(x)` от
`x^31` до `x^0`. `rs_32_parity_of_counting` — чётность байтов данных
0, 1, 2, ..., 222.

Векторы: `tests/vectors/py/reed_solomon.json`.

### 4.6 Зона данных и разнесение { #46-the-data-region-and-the-spread }

**Зона данных** занимает `D(T)` байт:

| Байты | Содержимое |
|---|---|
| `size` | файл |
| 1 | `L`, длина имени в байтах, от 0 до `NAME_MAX_BYTES` |
| `L` | имя файла в UTF-8 |
| остальные | заполнение (раздел 4.7) |

Имя длиннее `NAME_MAX_BYTES` байт в UTF-8 обрезается до наибольшего целого
числа знаков, которое помещается. Имя не охвачено отпечатком. Знак имени,
который нельзя закодировать в UTF-8 (одиночная суррогатная кодовая точка, от
U+D800 до U+DFFF), сохраняется как `?`.

Кодовое слово `j`, `0 <= j < m`, имеет в качестве байтов данных байты зоны
данных с `j * k` по `j * k + k - 1`. При чётности 0 кодовое слово — это его
255 байтов данных.

**Разнесение.** Байт `i` кодового слова `j` — это байт тела документа в позиции

    i * m + (j + i * SPREAD_STEP) mod m

Таким образом, байт `i` каждого кодового слова лежит в отрезке тела с `i * m`
по `(i + 1) * m - 1`, а 255 байтов одного кодового слова лежат в 255 разных
отрезках, разнесённых по всему документу: повреждение в одном месте отнимает
у каждого кодового слова несколько байт, вместо того чтобы отнять у нескольких
кодовых слов всё.

Последние `T * page_body - CODEWORD * m` байт тела (меньше `CODEWORD`) не
принадлежат никакому кодовому слову и являются заполнением.

Векторы: `tests/vectors/py/container.json`.

### 4.7 Заполнение { #47-padding }

Заполнение ничего не несёт. Существуют два варианта содержимого, и оба
действительны:

- optar 0.3.0 записывал нулевые байты;
- optar 0.3.1 и более поздние записывают **поток заполнения**: его блок `n`,
  `n = 0, 1, 2, ...`, — это `PADDING_BLOCK` байт значения SHA-256, вычисленного
  от `PADDING_KEY` с приписанным к нему `n` в виде 8 байт (старшим байтом
  вперёд); поток — это соединённые блоки. Заполнение зоны данных — это поток с его байта 0;
  заполнение в конце тела продолжает поток с того места, где остановилось
  заполнение зоны данных. (Нулевые байты печатаются белыми линиями поперёк
  каждой страницы; поток печатается как данные.)

Документ с любым другим заполнением всё равно остаётся действительным документом
для программы чтения (раздел 6.4), но только поток заполнения даёт те
страницы, которые печатает этот проект.

```example
padding_block_0 = d518824e181c15b2f69e390066efbfa00d73eb8f0c3d932313396940eedd1286
padding_bytes_30_to_33 = 12863e00
```

Векторы: `tests/vectors/py/container.json`.

### 4.8 Число страниц и ограничения { #48-the-page-count-and-the-limits }

Документ имеет наименьшее число страниц, вмещающее файл, байт длины и имя:

    need = size + 1 + L
    T    = the smallest T >= 1 with D(T) >= need

(`T` — наименьшее `T >= 1`, при котором `D(T) >= need`.)

Ограничения:

- `T <= MAX_PAGES`;
- при `parity > 0`: `T * page_bytes <= PROTECTED_MAX_BYTES`;
- `size < 2^64`, `L <= NAME_MAX_BYTES`.

Файл, которому нужно больше, поместить в документ нельзя.

```example
plan_need = 1000011
plan_codewords_needed = 4485
plan_pages = 6
plan_codewords = 4696
plan_data_bytes = 1047208
plan_body_bytes = 1197498
plan_spare_bytes = 18
plan_padding_in_region = 47197
plan_position_of_codeword_0_byte_0 = 0
plan_position_of_codeword_5_byte_0 = 5
plan_position_of_codeword_5_byte_1 = 7924
plan_position_of_codeword_5_byte_254 = 1194327
plan_page_of_codeword_5_byte_254 = 6
```

Пример — файл размером 1000000 байт с именем `vector.bin` на стандартных
страницах A4 с чётностью 32. Ему нужно 4485 кодовых слов; пять страниц вмещают
меньше, а шесть — `m = 4696`. В документе есть все 4696 кодовых слов; те, что
не нужны файлу, содержат заполнение. `plan_spare_bytes` — заполнение в конце
тела, а `plan_padding_in_region` — заполнение зоны данных. Позиции — это
позиции в теле документа (раздел 4.6).

Векторы: `tests/vectors/py/container.json`.

### 4.9 Что выдерживает документ (справочно) { #49-what-the-document-withstands-informative }

Потерянная страница стоит кодовому слову не более `ceil(page_body / m) + 1`
байт. Этот проект сообщает пользователю, что можно потерять любые `n` страниц,
если `n * (ceil(page_body / m) + 1) <= PROMISE_NUM * parity // PROMISE_DEN`;
при этом четверть чётности остаётся на повреждения оставшихся страниц. Это
обещание программ, а не свойство, на которое программа чтения может
полагаться или которое она должна контролировать.

### 4.10 От контейнера к страницам { #410-from-the-container-to-pages }

Поток имеет длину `T * net_bits // 8` байт. Если читать его как битовую строку,
полезная нагрузка страницы `p` (считая от 1) начинается с бита
`(p - 1) * net_bits`; все остальные биты равны 0. Если `net_bits` кратно 8,
поток — это просто соединённые полезные нагрузки. Если нет, у каждой страницы
после полезной нагрузки остаются `net_bits mod 8` неиспользуемых битов, и
полезные нагрузки некоторых страниц начинаются не с границы байта потока.

Поток печатается так, как сказано в разделе 2.7, что даёт ровно `T` страниц.
Надпись страницы — обычная строка надписи, произвольный текст которой
предназначен для людей: это имя файла (надпись, заданная пользователем, или имя
файла), одинаковое на всех страницах, и метки в нём нет. (Действительная метка
заставила бы программу чтения принять страницу за страницу документа с меткой,
раздел 6.1.)

С кодом Голея `net_bits mod 8` равно 0 или 4, и последняя полезная нагрузка
всегда заканчивается внутри потока. Этот проект печатает самоопознающиеся
документы только в десяти форматах страниц из раздела 5.2, и его программа
чтения ищет заголовки только в этих форматах.

```example
a4_medium_stream_bytes_for_3_pages = 344713
a4_medium_page_2_starts_at = 114904, 4
a4_medium_page_3_starts_at = 229809, 0
```

У страницы формата `0-50-70-24-3-1-2-24` `net_bits = 919236`, так что после её
114904 байт полезной нагрузки остаются 4 бита. Два значения — это байт потока,
в котором начинается полезная нагрузка страницы, и бит внутри этого байта
(0 — старший).

Векторы: `tests/vectors/py/container.json`, `tests/vectors/c/container_pages.json`.

### 5.3 PDF, который записывает этот проект { #53-the-pdf-this-project-writes }

Каждая страница документа — одна страница PDF, media box которой — бумага,
`[0 0 width height]` в пунктах. Изображение страницы — одно изображение
с 1 битом на пиксель (1 — белый), `width` на `height` пикселей страницы, без
интерполяции, нарисованное нижним левым углом в точке смещений макета
и масштабированное так, что один пиксель страницы равен одной точке данных:

    image width in points  = width  * dot size in points
    image height in points = height * dot size in points

(ширина и высота изображения в пунктах равны `width` и `height`, умноженным на
размер точки в пунктах.)

```example
a4_large_image_width_pt = 560.16
a4_large_image_height_pt = 802.08
```

PDF предназначен для печати в натуральную величину (100%). Ни один вектор не
закрепляет PDF; это делает `tests/unit/test_pdf.py`.

Изображения страниц записываются также в файлы PNG или PGM, по одному пикселю
изображения на пиксель страницы; векторы опознают страницу по SHA-256 её
двоичного файла PGM (`P5`), точные байты которого приведены в
`tests/vectors/README.md`: заголовок `P5\n<width> <height>\n255\n` в ASCII,
затем байты пикселей по строкам.

### 5.4 Лента надписи { #54-the-label-strip }

Надпись рисуется в пикселях страницы (раздел 2.8), поэтому на странице с более
крупными точками она вмещает меньше знаков: на самых крупных — слишком мало
даже для её собственной строки формата. Поэтому в PDF у страницы макета,
размер точек которого не `standard`, надпись заменяется **лентой надписи** —
вторым изображением, нарисованным стандартными точками данных:

- лента имеет `LABEL_HEIGHT` строк и
  `floor(data_width * printer dots per data dot / STANDARD_PRINTER_DOTS)`
  столбцов пикселей ленты (printer dots per data dot — число точек принтера на
  точку данных);
- она содержит строку надписи страницы, обрезанную и нарисованную, как в
  разделе 2.8, с шириной ленты вместо `data_width`;
- в изображении страницы полоса надписи закрашивается чёрным в столбцах от
  `border` до `border + data_width - 1`;
- лента рисуется поверх полосы с размером 0.36 pt на пиксель ленты, левым краем
  по левому краю столбцов данных полосы и по центру высоты полосы.

От страницы из части 2 отличается только полоса надписи; область данных и
рамка не затрагиваются. Страница такого макета в виде PNG или PGM сохраняет
надпись из раздела 2.8. Надпись самоопознающейся страницы не используется для
её опознания (раздел 6.2), поэтому программа чтения не обязана читать ленту.

```example
a4_large_strip_width = 1548
a4_large_strip_characters = 118
a4_large_strip_width_pt = 557.28
```

Векторы: `tests/vectors/c/container_pages.json` закрепляет страницы двух
макетов с более крупными точками как обычные страницы; ленту закрепляют
`tests/unit/test_font.py` и `tests/unit/test_pdf.py`.

## 6. Что должна делать программа чтения { #6-what-a-reader-must-do }

У программы чтения есть отсканированные страницы, и она каким-либо способом
прочитала с каждой из них биты данных и, где смогла, надпись. Эта часть
говорит, какие выводы она должна из них сделать. Сканам нельзя доверять:
одну страницу может напечатать кто угодно, и она может заявлять что угодно.

### 6.1 Действительная метка имеет приоритет над заголовком { #61-a-valid-tag-wins-over-a-header }

Для страницы в макете `standard` программа чтения должна сначала посмотреть на
надпись. Если надпись имеет вид, описанный в разделе 2.8, несёт строку формата
этого макета, число страниц не более `MAX_PAGES`, номер страницы от 1 до числа
страниц (или 1 при числе страниц 0), а её произвольный текст начинается с метки,
действительной для этих номера и числа страниц (раздел 3.2), то страница —
страница документа с меткой. Программа чтения должна обращаться с ней именно
так, даже если в её данных есть действительный заголовок.

Причина: поток самоопознающегося документа в том виде, в каком его возвращает
старая программа, можно снова напечатать как документ с меткой. На таких
страницах в данных лежат старые заголовки, и это страницы документа с меткой,
файл которого — этот поток.

### 6.2 Заголовку нельзя доверять { #62-a-header-is-untrusted }

Копия заголовка **корректна**, если её CRC верен, её сигнатура равна
`HEADER_MAGIC`, её версия равна `CONTAINER_VERSION`, её чётность равна 0, 32
или 64 и `1 <= page <= total`.

**Заголовок страницы** существует, если хотя бы одна из её `HEADER_COPIES`
копий корректна и все корректные копии равны. У страницы, корректные копии
которой различаются, заголовка нет.

Заголовок, прочитанный со страницы формата `F`, **допустим**, если он описывает
документ, который допускает раздел 4.8, то есть если выполнены все следующие
условия (`m`, `D` и `page_bytes` — как в разделе 4.1, для `F` и чётности
заголовка):

1. `total <= MAX_PAGES`;
2. `page_bytes // HEADER_COPIES >= HEADER_SIZE`;
3. если `parity > 0`: `total * page_bytes <= PROTECTED_MAX_BYTES`;
4. `size + 1 <= D(total)`: страницы вмещают файл и байт длины;
5. если `total > 1`: `size + 1 + NAME_MAX_BYTES > D(total - 1)`: никакое имя
   не позволило бы файлу поместиться на меньшее число страниц.

Программа чтения не должна использовать заголовок, который не является
допустимым. Правила 4 и 5 связывают число страниц с размером, так что заголовок
не может заявить много страниц для маленького файла или мало страниц для
большого.

Программа чтения должна расходовать память и время соразмерно переданным ей
страницам, а не тому, что заявляет заголовок: одна страница, заявляющая
документ из 9999 страниц, не должна заставлять программу чтения выделять
память под 9999 страниц или обрабатывать их.

Страницы относятся к одному документу, если их заголовки совпадают в
`fingerprint`, `size`, `total` и `parity` и страницы имеют один и тот же формат
страницы. Страницы другого документа не должны использоваться.

### 6.3 Проверенным файл делает только отпечаток { #63-only-the-fingerprint-verifies-a-file }

- **Самоопознающийся документ.** Байт полезной нагрузки — стирание, если один
  из его битов лежит в символе, который код страницы не смог скорректировать;
  каждый байт страницы, которая не была передана, — стирание. Файл — это первые
  `size` байт зоны данных, и он восстановлен, только если каждое кодовое
  слово, содержащее один из этих байтов, прочитано или исправлено (при
  чётности 0: не содержит стираний). Файл **проверен**, если он восстановлен
  и первые `FINGERPRINT_SIZE` байт его SHA-256 равны отпечатку из заголовка.
- **Документ с меткой.** Файл — это первые `SIZE` байт потока. Он **проверен**,
  если в нём `SIZE` байт и первые `FINGERPRINT_DIGITS` шестнадцатеричных знаков
  его SHA-256 равны отпечатку из метки.
- **Простой документ.** Ничто не делает его проверенным, и его длина
  неизвестна (раздел 2.7).

Программа чтения не должна называть файл проверенным ни по какой другой
причине. В частности, исправление, не сообщившее о неудаче, не делает файл
проверенным: кодовое слово, в котором неверных байтов больше, чем может
исправить его чётность, может превратиться в другое действительное кодовое
слово, а при чётности 0 вообще ничего не контролируется.

Имя файла (раздел 4.6) не охвачено отпечатком. Это текст, которому нельзя
доверять, даже если файл проверен, — как и любой надписи.

### 6.4 Заполнение никогда не читается { #64-padding-is-never-read }

Программа чтения не должна читать заполнение из раздела 4.7, контролировать
его или зависеть от него. Нулевые байты (0.3.0) и поток заполнения (0.3.1)
действительны оба, и документ с любым из них для программы чтения один и тот же
документ.

Байты зоны данных после имени — заполнение. Запись имени, байт длины которой
указывает за конец зоны данных, или байты которой не являются UTF-8, или
которая лежит в кодовом слове, которое не было исправлено, не даёт имени;
файл от этого не становится недействительным.

## 7. Эталонный декодер (справочно) { #7-reference-decoder-informative }

Эта часть описывает, как этот проект читает скан. Ничто из неё не обязательно:
программа чтения может находить страницу и снимать с неё отсчёты любым
способом. Шаги и их константы взяты из программы на C `unoptar` (часть 8);
результаты этого декодера на фиксированных сканах закреплены векторами,
названными в конце, чтобы он не изменился случайно.

### 7.1 Скан { #71-the-scan }

Скан читается как 8-битное изображение в оттенках серого в линейной шкале
яркости. Отсчёт `v` из файла превращается в
`floor(255 * (v / 255) ^ (1 / gamma) + 0.5)`, где `gamma` — гамма файла
(PNG `gAMA`) или 0.454545, если файл её не указывает. Цветное изображение
преобразуется по каналам, а затем каналы взвешиваются: 0.212671 красный,
0.715160 зелёный, 0.072169 синий, с округлением до ближайшего целого.
У 16-битного отсчёта сохраняются старшие 8 битов.

```example
linear_light_of_128 = 56
linear_light_of_200 = 149
```

### 7.2 Поиск страницы { #72-finding-the-page }

Декодеру дан формат страницы. Он работает с изображением в прямом положении.

1. **Уровни серого.** Порог сначала равен среднему значению серого. Не более
   32 раз: `black` — порог минус среднеквадратичное расстояние от порога до
   пикселей ниже него, `white` — порог плюс то же расстояние для пикселей выше
   него; новый порог равен `sync_white_cut * white + (1 - sync_white_cut) *
   black` с округлением; повторение прекращается, когда порог перестаёт
   меняться. Второй уровень, порог заливки, лежит посередине между `black`
   и `white`.
2. **Выделение страницы.** Белое поле вокруг страницы — это все пиксели не
   ниже порога заливки, связанные (через стороны, а не через углы) с одним из
   четырёх углов или четырёх середин краёв скана. Страница — всё остальное,
   что связано с центром скана. Все прочие пиксели (грязь между страницей
   и краем скана) делаются белыми.
3. **Разрыв рамки.** Если принтер обрезал край страницы, в рамке есть разрыв,
   белое поле вокруг страницы заходит между точками, и шаг 2 находит только
   часть страницы. Если найденная площадь меньше половины всего, что не
   относится к белому полю, белым полем вокруг страницы вместо этого считается
   то, до чего можно добраться через проходы шириной не менее `2 * r + 1`
   пикселей, где `r = max(5, longest side // 250) // 2` (longest side — длинная
   сторона скана); белые промежутки между точками меньше этой ширины. Этот результат
   используется, только если он даёт целую страницу. Это допуск данного
   декодера, а не свойство формата: у страницы рамка целая.
4. **Углы.** От каждого угла скана декодер идёт по диагонали внутрь и берёт
   первый пиксель ниже порога. Для этого страница должна быть в прямом
   положении, и её высота должна быть больше ширины; скан, у которого ширина
   больше высоты, сначала поворачивается (7.5).
5. **Размер пикселя.** Число пикселей скана на пиксель страницы по горизонтали
   и по вертикали получается из расстояний между углами, делённых на `width`
   и `height`; направления строк и столбцов страницы — из средних
   противоположных сторон. (Горизонтальный размер использует верхний левый
   угол дважды, а нижний левый не использует вовсе. Это унаследованное
   поведение декодера, а не часть формата.)

### 7.3 Кресты { #73-crosses }

Первый крест ожидается в `border + chalf` пикселях страницы внутрь от верхнего
левого угла. Каждый следующий крест ожидается на один шаг правее своего левого
соседа, а первый крест строки — на один шаг ниже креста над ним, так что каждый
поиск начинается от уже найденного креста. Для каждого креста:

1. грубый поиск с шагом в целый пиксель скана, на расстояние до половины
   полустороны креста в каждом направлении, места, где изображение лучше всего
   коррелирует с узором креста (тёмная, светлая, светлая, тёмная четверти);
2. точный поиск в пределах половины пикселя скана с шагом в четверть пикселя,
   по кресту, уменьшенному на `cross_trim` пикселей страницы с каждой стороны;
3. собственный порог: по пикселям креста вычисляются `white` и `black`, как
   в 7.2, и объединяются как `white_cut * white + (1 - white_cut) * black`.

### 7.4 Снятие отсчётов и декодирование { #74-sampling-and-decoding }

1. **Фильтры.** Удаляются тёмные пятнышки, ширина которых меньше
   `minmax_filter` размеров пикселя страницы (проходы фильтра максимума, затем столько же проходов фильтра
   минимума); затем изображение размывается ядром 3 на 3 (1 2 1 /
   2 4 2 / 1 2 1) `round(pixel area * pixel_blur ^ 2)` раз (pixel area —
   площадь пикселя страницы в пикселях скана).
2. **Снятие отсчётов.** Положение каждого пикселя данных на скане
   интерполируется между четырьмя окружающими его крестами, и так же его порог.
   К отсчёту применяется повышение резкости: `value + unsharp_mask * (value - mean of the four
   neighbours at unsharp_dist page pixels)` (mean — среднее четырёх соседей на
   расстоянии `unsharp_dist` пикселей страницы). Бит равен 1, если результат
   ниже порога.
3. **Декодирование.** Биты снова собираются в символы (раздел 2.6). Символ
   Голея заменяется ближайшим символом, если тот отличается не более чем
   в 3 битах; иначе символ неисправим, и его старшие 12 битов берутся такими,
   как прочитаны. В символе Хэмминга корректируется один неверный бит; два неверных
   бита делают его неисправимым.
4. Слова страницы соединяются в её `net_bits` битов данных. Для простого
   документа или документа с меткой биты страниц соединяются в порядке страниц
   и разрезаются на байты; биты, не составляющие последнего целого байта,
   отбрасываются.

```example
decoder_unsharp_mask = 7
decoder_unsharp_dist = 1
decoder_sync_white_cut = 0.1
decoder_white_cut = 0.06
decoder_minmax_filter = 0.5
decoder_pixel_blur = 0.25
decoder_cross_trim = 0.75
```

### 7.5 Опознание скана { #75-identifying-a-scan }

Если формат страницы не задан, этот проект определяет его сам:

1. Контур страницы (7.2, шаги с 1 по 4) даёт её форму. Два вида бумаги
   пробуются в порядке близости формы к их странице `standard`; каждый
   пробуется в прямом положении и повёрнутым на пол-оборота (или на четверть
   оборота в любую сторону для скана, у которого ширина больше высоты).
2. Для каждой бумаги сначала пробуется её страница `standard`: страница
   находится, и её надпись читается сопоставлением каждой ячейки знака со
   шрифтом. Действительная метка решает сразу (раздел 6.1). Надпись без метки
   принимается, только если она прочитана чётко, и тогда данные всё равно
   просматриваются в поисках заголовка, потому что у самоопознающейся страницы
   со стандартными точками именно такая надпись.
3. Затем макеты этой бумаги, начиная с самого близкого по форме: страница
   находится, декодируется, и решает допустимый заголовок (раздел 6.2).

Неверно прочитанная метка проходит контроль примерно в одном случае из 256; у надписи без метки контрольного значения нет вовсе,
поэтому она должна быть прочитана чётко, и поэтому отвергается произвольный
текст, который отличается от действительной метки одним неверно прочитанным
знаком. Эти пороги принятия относятся к этой программе чтения, а не к формату.

### 7.6 Медленный метод чтения { #76-the-slower-reader }

Если шаги из 7.5 ничего не опознали, но контур страницы найден, или если они
приняли страницу только по надписи без метки на скане, где на пиксель данных
приходится меньше 2.5 пикселя скана, а 1% или больше символов страницы не
поддаётся коррекции, этот проект пробует второй, более медленный метод чтения
(`src/optar/decoder/soft.py`), предназначенный для скана со слишком низким
для его размера точек разрешением. Для каждого возможного макета и поворота,
в порядке из 7.5, он:

1. увеличивает скан так, чтобы пиксель данных имел ширину около четырёх
   пикселей скана, и находит страницу, как в 7.2 и 7.3;
2. читает страницу, как в 7.4, и считает известными символы, декодированные
   не более чем с одним скорректированным битом;
3. снимает отсчёты в сетке 7 на 7 точек с шагом в половину пикселя данных
   вокруг каждого пикселя данных и методом наименьших квадратов подбирает
   фильтр, переводящий эти отсчёты в известные биты, — по одному фильтру для
   каждой из 16 на 22 областей страницы;
4. применяет фильтры к каждому пикселю данных, что даёт для каждого бита
   уверенность со знаком, и выбирает для каждого символа Голея кодовое слово,
   лучше всего соответствующее его 24 значениям уверенности;
5. считает известными 60% символов с наибольшей уверенностью и повторяет всё
   с шага 3, всего пять подборов.

Страница принимается только по допустимому заголовку (раздел 6.2). Надпись не
читается, поэтому страница без заголовка (простой документ или документ
с меткой, часть 3) этим способом не опознаётся. Страница, метка которой была
принята, никогда не читается этим способом, так что раздел 6.1 соблюдается.
Результат передаётся
в контейнер точно так же, как результат обычного метода чтения, и проверенным
файл делает только отпечаток (раздел 6.3). Ничто в этом методе чтения не
является частью формата, и он не меняет результатов декодера из разделов с 7.1
по 7.5.

Векторы: `tests/vectors/c/decoder.json`, `tests/vectors/c/decoder_internals.json`
(они закрепляют результаты этого декодера на фиксированных сканах, а не формат).

## 8. История { #8-history }

Страница из части 2 — это формат Twibright Optar, программы на C, которую
написал Карел Кулгави (Karel Kulhavy) в 2007 году и которую с 2012 года
сопровождали в `colindean/optar`. Её исходные тексты хранятся без изменений
в папке `lega-c` этого проекта в том виде, в каком они были в коммите
`9c8379c25466bf142459a26b0f34521bdde2af12` того репозитория. Векторы
в `tests/vectors/c` записаны с помощью той программы, а векторы
в `tests/vectors/py` — с помощью этого проекта.

| Версия | Что добавлено |
|---|---|
| Программа на C | страница (часть 2); A4 или Letter выбирается при компиляции |
| 0.1.0 | те же страницы, записываемые и читаемые этим проектом |
| 0.2.0 | метка (часть 3) |
| 0.3.0 | контейнер, размеры точек и макеты (части 4 и 5), с нулевым заполнением |
| 0.3.1 | поток заполнения (раздел 4.7) |

Что формат сохраняет от программы на C:

- рамку, кресты, порядок пикселей данных и перемежение;
- таблицу кода Голея, построенную по додекаэдру, и коды Хэмминга;
- ленту шрифта, строку надписи и три её особенности (раздел 2.8);
- предел в 9999 страниц и пустой файл, печатаемый как одна страница `1/0`;
- то, что страница не записывает длину своего потока;
- сетки двух макетов `standard` и смещения макета Letter.
  Программы на C размещали страницу A4 со смещениями 19.22 и 17.44 pt, что не
  приходится на целые точки принтера; этот проект размещает её со смещениями
  из раздела 5.2.

В программу на C вкомпилирован один формат страницы. Её декодер принимает
строку формата как аргумент, но использует только последнее поле.

В надписи осталось одно отличие от программы на C: программа на C обрезала
строку надписи по байтам, а этот формат обрезает её по знакам. Оба способа
дают одну и ту же страницу, если только строка не обрезается и не содержит
знаков вне ASCII до места обрезки.

Поведение декодера, унаследованное от программы на C и не являющееся частью
формата (часть 7): семь констант из раздела 7.4, двойное использование одного
угла при вычислении размера пикселя, поиск углов, требующий страницы в прямом
положении, у которой высота больше ширины, и арифметика с 32-битными числами
с плавающей точкой, которую закрепляют векторы декодера.
